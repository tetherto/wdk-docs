WDK CLI includes the `wdk-mcp` Model Context Protocol server. It exposes wallet operations as structured tools over stdio and routes wallet-dependent operations to the same local daemon used by the CLI.

<Callout type="warn">
Use a dedicated development wallet with limited funds. On Unix-like systems, while a wallet is unlocked, any process running as the same OS user that can connect to the owner-only daemon socket can request signing or sending without another passphrase.
</Callout>

## Prepare A Wallet

Install WDK CLI with the command in [Install](/cli/#install). This guide deliberately uses a dedicated development wallet and Sepolia test funds; the general Get Started guide uses Ethereum mainnet.

If `agent-dev` is your first wallet, it becomes the default automatically:

```bash title="Terminal"
wdk wallet create --name agent-dev --words 12
wdk wallet unlock --name agent-dev --ttl 5
```

Enter and confirm a strong, non-empty passphrase when the create command prompts, then record the generated seed phrase offline.

If another wallet is already the default, select `agent-dev` explicitly:

```bash title="Terminal"
wdk wallet default --name agent-dev
```

Wallet-dependent MCP tools use the default wallet unless the request includes `wallet`. The wallet must be unlocked before those tools run.

The TTL is absolute from unlock; MCP activity does not extend it. Use a short TTL during development and lock the wallet when the session ends.

## Configure An MCP Client

Choose one setup target:

```bash title="Claude Desktop"
wdk mcp setup --ai-tool claude-desktop
```

```bash title="Claude Code"
wdk mcp setup --ai-tool claude-code
```

```bash title="OpenClaw"
wdk mcp setup --ai-tool openclaw
```

| Target | Setup behavior |
| --- | --- |
| Claude Desktop | Adds `wdk-wallet` under `mcpServers` in the platform-specific Claude Desktop JSON config. |
| Claude Code | Runs `claude mcp add -s user wdk-wallet -- ...` with the current Node.js executable and installed MCP script. |
| OpenClaw | Runs `openclaw mcp set wdk-wallet ...` with the current Node.js executable and installed MCP script. |

Setup checks whether the target appears to be installed, tests the MCP server when possible, and reports the restart action required by that client.

Verify one target:

```bash title="Terminal"
wdk mcp verify-setup --ai-tool claude-desktop
```

List the configuration status of all three targets:

```bash title="Terminal"
wdk mcp list
```

Remove a target configuration with:

```bash title="Terminal"
wdk mcp remove --ai-tool claude-desktop
```

Replace `claude-desktop` with `claude-code` or `openclaw` as needed.

### Other MCP Clients

`wdk-mcp` is a standard stdio MCP server. For clients that accept the common `mcpServers` JSON shape, add:

```json
{
  "mcpServers": {
    "wdk-wallet": {
      "command": "wdk-mcp"
    }
  }
}
```

This configuration requires the client process to find `wdk-mcp` on its `PATH`. If the client uses a different configuration shape or does not inherit your shell `PATH`, configure a stdio server named `wdk-wallet` and point its command to the installed `wdk-mcp` executable.

## Available MCP Tools

| Tool | Wallet required | Purpose |
| --- | --- | --- |
| `get_networks` | No | List networks, optionally filtered to mainnets or testnets. |
| `list_tokens` | No | List every registered token or filter by network. |
| `get_token` | No | Read one network and token registry entry. |
| `get_address` | Yes | Derive one address or addresses across networks. |
| `get_balance` | Yes | Read one balance or aggregate native balances with USD estimates. |
| `get_history` | Yes | Query indexer-backed token-transfer history for one network. |
| `list_methods` | No | List the chain-specific methods declared by one built-in wallet module or every module in the catalog. |
| `call_method` | Yes | Invoke one catalog-declared chain-specific wallet method. |
| `send_token` | Yes | Preview or execute a native or registered-token transfer. |
| `sign_message` | Yes | Sign an arbitrary message with the selected account key. |
| `verify_message` | Yes | Verify a message and signature against the selected account key. |
| `get_transaction` | Yes | Read a normalized receipt, optionally waiting for confirmed or final status. |
| `swap_token` | Yes | Preview or execute a same-network or cross-network token swap. |
| `bridge_token` | Yes | Preview or execute an exact-input, same-token bridge between networks. |
| `buy_crypto` | Yes | Create a signed MoonPay buy URL. |
| `sell_crypto` | Yes | Create a signed MoonPay sell URL. |

`get_history` needs indexer configuration. `buy_crypto` and `sell_crypto` need MoonPay configuration. See [Configuration](/cli/configuration/).

## CLI Capabilities Not Exposed Over MCP

`wdk-mcp` registers only the sixteen tools listed above. Through this server, an agent can operate a wallet that a person has already unlocked, but it cannot call the CLI's wallet administration or persistent-configuration commands.

- Wallet administration: `wdk wallet create`, `import`, `export`, `unlock`, `lock`, `delete`, `rename`, and `default`. These commands create, import, or reveal seed material; confirm wallet ownership; change wallet identity or default selection; or control an unlock session. `wdk wallet unlock` is deliberately the human authorization moment, and `wdk wallet lock` ends that session.
- Persistent configuration: `wdk config set` and `reset`, `wdk network create` and `delete`, `wdk token add` and `delete`, and `wdk module add` and `remove`. These commands change durable local configuration or installed executable code and remain user-driven decisions.

This is a boundary of the MCP tool surface, not an operating-system sandbox. An AI client with separate shell access is outside this boundary and may be able to invoke `wdk` directly.

## Preview And Confirm Transactions

`send_token`, `swap_token`, and `bridge_token` default to `dryRun: true`. The recommended client workflow is:

1. Call the tool without `dryRun`, or with `dryRun: true`.
2. Show the wallet, account index, networks, tokens, recipient, amounts, route, fees, and skipped protocols that apply.
3. Ask the user to confirm those exact values.
4. Call the same tool with `dryRun: false` only after confirmation.

The following examples are argument objects for `send_token`. See [Swap and Bridge](/cli/guides/swap-and-bridge) for the fields used by `swap_token` and `bridge_token`.

Example `send_token` preview request:

```json
{
  "network": "sepolia",
  "to": "<recipient-address>",
  "amount": "0.0001",
  "wallet": "agent-dev"
}
```

Example `send_token` execution request after confirmation:

```json
{
  "network": "sepolia",
  "to": "<recipient-address>",
  "amount": "0.0001",
  "wallet": "agent-dev",
  "dryRun": false
}
```

<Callout type="error">
The preview-and-confirm sequence is guidance for the AI client; the daemon does not enforce it. A direct `send_token`, `swap_token`, or `bridge_token` call with `dryRun: false` executes when the selected wallet is unlocked and the request is otherwise valid.
</Callout>

For `swap_token`, provide exactly one of the decimal-string fields `amountIn` and `amountOut`. `toNetwork` is optional. For `bridge_token`, provide the exact-input `amount`; the same registered token moves between two different networks. If `recipient` is omitted, the daemon derives the destination address from the selected wallet and the same account index.

Swap and bridge execution requests fresh quotes. The route, amounts, or skipped protocols can therefore differ from the earlier preview. Exact-input routing ranks successful quotes by highest output, and exact-output routing ranks them by lowest input. Separate gas and bridge fees are shown but excluded from route ranking. See [Swap and Bridge](/cli/guides/swap-and-bridge).

## Sign And Verify Messages

`sign_message` accepts `network`, `message`, and optional `wallet` and `index` fields. Show those exact values and obtain explicit user confirmation before calling it.

<Callout type="error">
`sign_message` signs immediately. It has no dry run, confirmation prompt, or second passphrase check, and the daemon does not enforce the tool description's confirmation guidance. A signature can authorize actions on some chains.
</Callout>

`verify_message` accepts the same account fields plus `signature` and returns whether that account verifies the message and signature. Both tools require the selected wallet to be unlocked.

## Read A Transaction

`get_transaction` requires `network` and `hash`, with optional `wallet` and `index` fields. Omit `finality` to return the account's current normalized receipt without waiting. Set `finality` to `confirmed` or `final` to wait for that target. When you set `finality`, use a positive integer `timeout` in milliseconds; the default finality wait is 150,000 milliseconds. Beta.5's MCP schema accepts any number and does not enforce positivity or integrality, so validate this value in the client.

Module-specific receipt fields are retained. Returned `bigint` values are decimal strings.

## Call Module Methods

Use `list_methods` before `call_method`. Omit `network` from `list_methods` to inspect every built-in module with declared methods, or provide a registered network to get its exact method and parameter schema.

`call_method` accepts:

| Field | Required | Description |
| --- | --- | --- |
| `network` | Yes | Registered network |
| `name` | Yes | Exact method name returned by `list_methods` |
| `args` | As declared | String-valued object keyed by the declared camel-case parameter names |
| `index` | No | Account index; defaults to `0` |
| `wallet` | No | Wallet name; defaults to the selected wallet |

Use decimal integer strings for `bigint` parameters. Encode a structured parameter as a JSON string, including quoted decimal strings for nested `bigint` values.

<Callout type="error">
Methods marked `write` can move funds or mutate state. `call_method` has no dry-run or enforced confirmation. Show the exact wallet, network, method, and arguments to the user and call it only after explicit confirmation. The method's `kind` is catalog metadata for the client; the daemon does not use it as an authorization control.
</Callout>

The method allowlist comes from the built-in beta.5 catalog. The server does not reflect over arbitrary methods from custom module packages. See [Call Module Methods](/cli/guides/call-module-methods) for CLI examples and parameter formats.

## Security And Session Boundaries

- The AI client sends tool parameters to `wdk-mcp`; it does not send the wallet seed or passphrase as tool input.
- Wallet operations cross the local daemon endpoint. On Unix-like systems, owner-only socket permissions block other OS users, not other processes running as the wallet owner.
- An unlocked wallet behaves like a local hot wallet for the session. Read, signing, and send operations do not ask for the passphrase again.
- `--ttl 0` disables automatic expiry for that wallet. Prefer a finite TTL.
- Prompts or client-side confirmation dialogs are not daemon authorization controls.

Read [Security Model](/cli/reference/security-model/) before exposing an unlocked wallet to an AI client or local automation.

Lock the wallet when the session is finished:

```bash title="Terminal"
wdk wallet lock --name agent-dev
```

## When To Use The MCP Toolkit

Use [MCP Toolkit](/ai/mcp-toolkit/) when you need to build and control an MCP server in application code, select individual WDK tools, or add custom tools.

Use the WDK CLI MCP server when you want the bundled tool set and local wallet daemon, with automated setup for Claude Desktop, Claude Code, and OpenClaw or manual stdio configuration for another MCP-compatible client.
